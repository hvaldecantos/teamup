# PRD: Normalized Scorer (Sum-Based Aggregation)

## Problem Statement

Teams need a scorer that balances total group power across attributes while still being robust to different attribute scales. The current normalized scorer concept uses group means after normalization. That treats unequal-size groups as fair when their averages match, even if one group has materially more total contribution than another.

In practical partitioning, this can produce outcomes that look mathematically balanced but are operationally unbalanced. For example, one group can have more entities with the same per-entity average and still be judged equivalent.

## Solution

Introduce a renamed and clarified normalized scoring model where:

- Attribute values are still globally normalized to [0, 1].
- Group aggregation uses sum of normalized values per attribute, not mean.
- Per-attribute imbalance is computed as max group sum minus min group sum.
- Final score remains the maximum across attribute imbalances for the default strategy.

This keeps normalization benefits (scale fairness across attributes) while aligning fairness to total group contribution.

## User Stories

1. As a developer, I want normalized scoring to compare total group contribution per attribute, so that partitions reflect overall group power.
2. As a developer, I want unequal group sizes to influence normalized scoring naturally, so that larger groups are not treated as equivalent only by average.
3. As a developer, I want global normalization to remain in place, so that attributes with different numeric ranges are still comparable.
4. As a developer, I want the base normalized scorer to have a name that matches its behavior, so that API names are clear and unsurprising.
5. As a developer, I want the normalized base class to be named NormalizedScorer, so that the name does not imply mean-based logic.
6. As a developer, I want the default normalized max strategy to continue working, so that optimization behavior remains conservative.
7. As a developer, I want zero-variance attributes to contribute zero to the score, so that constant attributes do not add noise.
8. As a developer, I want existing scorer validation behavior preserved for invalid inputs, so that callers keep receiving clear errors.
9. As a developer, I want scorer implementations to remain interchangeable through the scoring interface, so that partition orchestration does not need redesign.
10. As a developer, I want the normalized scorer score interpretation to align with sum-based balancing, so that test expectations and docs are coherent.
11. As a developer, I want backward compatibility for the old class name during migration, so that existing imports do not break immediately.
12. As a developer, I want deprecation guidance for old naming, so that migration to the new naming is predictable.
13. As a developer, I want tests to validate sum-based normalization behavior directly through score outcomes, so that regressions are caught early.
14. As a developer, I want multi-group scenarios covered by tests, so that sum-based behavior is trustworthy beyond two-group cases.
15. As a developer, I want mixed-size group cases covered by tests, so that known fairness gaps from mean-based aggregation do not return.
16. As a developer, I want score semantics documented clearly, so that consumers understand what lower and higher values represent.

## Implementation Decisions

- Keep the same scorer abstraction and extension pattern.
- Rename the abstract normalized base scorer to NormalizedScorer.
- Preserve the two-phase architecture:
  1. Normalize all entity attributes globally.
  2. Aggregate each attribute within each group using sum of normalized values.
- Compute per-attribute differences as max group sum minus min group sum.
- Keep the max-combination strategy as the default concrete behavior.
- Keep error contracts unchanged for empty groups, empty attributes, and empty inner groups.
- Preserve behavior for missing attributes through existing entity attribute access behavior.
- Introduce migration compatibility by retaining the old class name as an alias for one transition cycle.
- Update scorer documentation and terminology to remove mean-based language where behavior is sum-based.

Deep module boundaries:

- Normalization module logic remains a deep reusable unit inside the normalized base scorer.
- Aggregation and difference orchestration remain centralized in one score pipeline, minimizing duplication in concrete scorers.
- Combination strategy remains isolated in overridable behavior for future average or RMS variants.

## Testing Decisions

- Good tests validate external scoring outcomes for representative partitions and avoid asserting internal temporary structures.
- Tests should hand-calculate expected scores from normalized sums and compare with scorer outputs.
- Test coverage should include:
  - Abstract base scorer cannot be instantiated directly.
  - Balanced equal groups return zero.
  - Full-range unbalanced groups return expected max difference.
  - Mixed group sizes verify sum-based distinction from mean-based behavior.
  - Multiple attributes verify max-combination behavior.
  - Three or more groups verify generalized difference logic.
  - Zero-variance attributes contribute zero.
  - Floating-point values remain numerically stable.
  - Validation and error scenarios remain unchanged.
- Migration tests should confirm old naming remains importable during transition when aliasing is used.
- Prior art should continue following existing scorer test style: inline entities, explicit comments for expected math, and behavior-first assertions.

## Out of Scope

- Introducing new weighting systems per attribute.
- Redefining partitioning algorithm search strategy.
- Changing default scorer selection in builder or orchestration flows.
- Adding score post-scaling to force fixed numeric ranges across all dataset sizes.
- Performance optimization such as caching normalized values between scorer invocations.
- Redesigning entity schema or partition data models.

## Further Notes

This PRD intentionally changes fairness semantics from average contribution parity to total normalized contribution parity. That is the central product decision.

Because sums are used after normalization without additional scaling, score magnitude can vary with group sizes and entity counts. This is accepted by design for the current iteration.

If needed later, a separate enhancement can introduce an optional normalized-sum scaling mode without changing the default behavior defined here.
